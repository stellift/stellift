Esse bug apareceu num marketplace que fizemos em Elixir. Cadastrar um serviço chamado "Integração de pagamento Pix e cartão" dava erro no Postgres:

```
ERROR 22021 (character_not_in_repertoire) invalid byte sequence for encoding "UTF8": 0xc3 0xc3
```

Com título sem acento, funcionava. O slug vinha desta função:

```elixir
defp generate_slug(title) do
  title
  |> String.downcase()
  |> String.replace(~r/[^\w\s-]/, "")
  |> String.replace(~r/\s+/, "-")
  |> String.slice(0, 100)
end
```

O problema é a regex sem a flag `u`. Sem ela, o Elixir olha o texto byte a byte, e em UTF-8 o "ç" ocupa dois bytes, `0xC3 0xA7`, assim como o "ã", `0xC3 0xA3`.

Byte a byte, o `\w` usa a tabela Latin-1. Por ela, `0xC3` é a letra "Ã", então fica. Já `0xA7` é "§" e `0xA3` é "£", que não são letras, então saem. De "ção" sobra `0xC3 0xC3 0x6F`, que não é UTF-8 válido, e por isso o erro fala em `0xc3 0xc3`.

Dá para conferir no `iex`:

```elixir
Regex.run(~r/\w/, <<0xC3>>)
# [<<195>>]

Regex.run(~r/\w/, <<0xA7>>)
# nil
```

Colocar a flag `u` já acaba com o erro, porque aí a regex olha caracteres inteiros. Só que o slug ficaria com acento, e endereço com acento vira `integra%C3%A7%C3%A3o` quando alguém copia o link. Então aproveitamos para tirar os acentos antes:

```elixir
defp generate_slug(title) do
  title
  |> :unicode.characters_to_nfd_binary()
  |> String.replace(~r/\p{Mn}/u, "")
  |> String.downcase()
  |> String.replace(~r/[^a-z0-9\s-]/u, "")
  |> String.replace(~r/[\s-]+/u, "-")
  |> String.trim("-")
  |> String.slice(0, 100)
end
```

O `characters_to_nfd_binary` separa o "ç" em "c" mais o acento, e o `\p{Mn}` apaga o acento. Fica assim:

```
Integração de pagamento Pix e cartão  ->  integracao-de-pagamento-pix-e-cartao
Café & Pão                            ->  cafe-pao
```

Se você tem regex rodando em texto que o usuário digita, procure no projeto por `~r/` sem o `u` no final. As que usam `\w`, `\s` ou classe negada são as que quebram com acento.
