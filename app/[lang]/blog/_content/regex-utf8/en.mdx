This bug showed up in a marketplace we built in Elixir. Creating a service called "Integração de pagamento Pix e cartão" made Postgres throw:

```
ERROR 22021 (character_not_in_repertoire) invalid byte sequence for encoding "UTF8": 0xc3 0xc3
```

Titles without accents worked fine. The slug came from this function:

```elixir
defp generate_slug(title) do
  title
  |> String.downcase()
  |> String.replace(~r/[^\w\s-]/, "")
  |> String.replace(~r/\s+/, "-")
  |> String.slice(0, 100)
end
```

The problem is the regex without the `u` flag. Without it, Elixir looks at the text byte by byte, and in UTF-8 "ç" takes two bytes, `0xC3 0xA7`, and so does "ã", `0xC3 0xA3`.

Byte by byte, `\w` uses the Latin-1 table. There `0xC3` is the letter "Ã", so it stays. But `0xA7` is "§" and `0xA3` is "£", which aren't letters, so they go. What's left of "ção" is `0xC3 0xC3 0x6F`, which isn't valid UTF-8, and that's why the error mentions `0xc3 0xc3`.

You can check it in `iex`:

```elixir
Regex.run(~r/\w/, <<0xC3>>)
# [<<195>>]

Regex.run(~r/\w/, <<0xA7>>)
# nil
```

Adding the `u` flag already gets rid of the error, because then the regex looks at whole characters. But the slug would keep its accents, and a URL with accents turns into `integra%C3%A7%C3%A3o` when someone copies the link. So we also strip the accents first:

```elixir
defp generate_slug(title) do
  title
  |> :unicode.characters_to_nfd_binary()
  |> String.replace(~r/\p{Mn}/u, "")
  |> String.downcase()
  |> String.replace(~r/[^a-z0-9\s-]/u, "")
  |> String.replace(~r/[\s-]+/u, "-")
  |> String.trim("-")
  |> String.slice(0, 100)
end
```

`characters_to_nfd_binary` splits "ç" into "c" plus the accent, and `\p{Mn}` deletes the accent. You end up with:

```
Integração de pagamento Pix e cartão  ->  integracao-de-pagamento-pix-e-cartao
Café & Pão                            ->  cafe-pao
```

If you have regexes running on text users type, search your project for `~r/` without a `u` at the end. The ones using `\w`, `\s` or a negated class are the ones that break on accents.
